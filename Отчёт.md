# Отчёт: Task Manager — приложение по методологии 12 факторов

## 1. Доменная область

**Task Manager** — персональный менеджер задач. Пользователь регистрируется, входит в систему по email и паролю и ведёт собственный список задач: создаёт, просматривает, редактирует, меняет статус, ищет по названию и удаляет. Пользователь видит только свои задачи, чужие задачи для него не существуют (API отвечает `404`).

Функциональность:

| Требование | Реализация |
|---|---|
| Регистрация (имя, email, пароль) | `POST /api/auth/register` |
| Вход по email и паролю | `POST /api/auth/login` → JWT access token |
| Выход (завершение сессии) | `POST /api/auth/logout`: `jti` токена заносится в таблицу `revoked_tokens`, после чего токен отклоняется всеми репликами API |
| Создание задачи (название, описание, статус, приоритет, срок) | `POST /api/tasks` |
| Список своих задач (название, статус, приоритет, срок, дата создания) | `GET /api/tasks?page=&pageSize=` |
| Просмотр задачи | `GET /api/tasks/{id}` |
| Редактирование задачи | `PUT /api/tasks/{id}` |
| Изменение статуса (`Todo` / `InProgress` / `Done`) | `PATCH /api/tasks/{id}/status` |
| Удаление с подтверждением | `DELETE /api/tasks/{id}`; подтверждение запрашивает UI (`window.confirm`) |
| Поиск по названию | `GET /api/tasks?search=...`: `ILIKE` с trigram-индексом GIN |
| Пагинация | `page`, `pageSize` (по умолчанию 20, не больше 100); ответ содержит `totalCount` и `totalPages` |

Дополнительно: фильтр по статусу `GET /api/tasks?status=Done`, текущий пользователь `GET /api/auth/me`, health-checks `/health/live` и `/health/ready`.

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Backend | C# 12, .NET 8 (LTS), ASP.NET Core Web API (controllers), EF Core 8, Npgsql, JWT Bearer |
| БД | PostgreSQL 16 (расширение `pg_trgm`) в отдельном контейнере |
| Frontend | React 18 + TypeScript, Vite, React Router |
| Раздача фронтенда и reverse-proxy | nginx 1.27 (alpine) |
| Тесты | xUnit, `WebApplicationFactory`, Testcontainers (реальный PostgreSQL 16) |
| Инфраструктура | Docker, Docker Compose, Makefile, `dotnet-ef` (закреплён локальным tool-манифестом) |

Протокол — HTTP/1.1 REST с JSON, ошибки в формате RFC 7807 (`ProblemDetails`).

Стек выбран нетребовательным к ресурсам: итоговые образы весят ~170 МБ (API на `aspnet:8.0-alpine`) и ~75 МБ (web на `nginx:alpine`); без брокеров, кэшей и отдельного identity-сервера. По замерам `docker stats` в простое одна реплика API занимает около 70 МБ RAM, PostgreSQL — около 40 МБ, nginx — около 15 МБ, то есть весь стек укладывается примерно в 130 МБ.

## 3. Архитектура

```
TwelveFactorApp/
├── backend/
│   ├── src/
│   │   ├── TaskManager.Domain          доменные модели и инварианты, без зависимостей
│   │   ├── TaskManager.Application     сценарии (AuthService, TaskService), интерфейсы портов, DTO
│   │   ├── TaskManager.Infrastructure  EF Core, репозитории, read-провайдеры, хеширование паролей, миграции
│   │   └── TaskManager.Api             контроллеры, JWT, обработка ошибок, admin-команды, composition root
│   ├── tests/TaskManager.Tests         unit + интеграционные тесты
│   └── Dockerfile
├── frontend/                           React + TS, nginx-шаблон, Dockerfile
├── docker-compose.yml                  db, migrator, api, web
├── k8s/                                манифесты для развёртывания в Kubernetes (minikube)
├── Makefile                            все команды сборки, запуска и миграций
└── .env.example                        шаблон конфигурации
```

Зависимости направлены внутрь: `Api → Infrastructure → Application → Domain`. Application объявляет интерфейсы:

- **запись (write side):** `IUserRepository`, `ITaskRepository`, `IUnitOfWork` работают с доменными агрегатами, инварианты проверяет домен;
- **чтение (read side):** `ITaskQueryProvider`, `IUserQueryProvider` возвращают сразу DTO через `AsNoTracking()` и `Select`-проекцию. Материализации сущностей и change tracking нет, из БД читаются только нужные колонки, поэтому выдача списка быстрая;
- **инфраструктурные порты:** `IPasswordHasher` (PBKDF2-SHA256, 100 000 итераций), `IAccessTokenIssuer` (JWT HS256), `ITokenRevocationStore`.

Реализации регистрируются в DI extension-методами каждого слоя: `AddApplication()`, `AddInfrastructure()`, `AddJwtAuthentication()`.

## 4. Основные сущности

### User — пользователь

| Поле | Тип (PostgreSQL) | Ограничения |
|---|---|---|
| `id` | `uuid` | PK |
| `name` | `varchar(100)` | обязательно |
| `email` | `varchar(256)` | обязательно, уникальный индекс, хранится в нижнем регистре |
| `password_hash` | `text` | формат `v1.{iterations}.{salt}.{hash}` |
| `created_at` | `timestamptz` | |

### TaskItem — задача (агрегат, принадлежит пользователю)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `uuid` | PK |
| `user_id` | `uuid` | FK → `users.id`, `ON DELETE CASCADE` |
| `title` | `varchar(200)` | обязательно; GIN-индекс `gin_trgm_ops` для поиска `ILIKE '%...%'` |
| `description` | `varchar(4000)` | может быть пустым |
| `status` | `varchar(20)` | `Todo`, `InProgress`, `Done` |
| `priority` | `varchar(20)` | `Low`, `Medium`, `High` |
| `due_date` | `date` | необязательно |
| `created_at`, `updated_at` | `timestamptz` | составной индекс `(user_id, created_at DESC)` под постраничную выдачу |

Перечисления хранятся строками: так данные читаемы в БД и не ломаются при переупорядочивании enum.

### RevokedToken — отозванный токен (инфраструктурная сущность)

| Поле | Тип | |
|---|---|---|
| `token_id` | `varchar(64)` | PK (`jti` из JWT) |
| `expires_at` | `timestamptz` | индекс; по нему admin-команда `purge-revoked-tokens` чистит устаревшие записи |

Доменные правила сосредоточены в `User.Register`, `TaskItem.Create`, `TaskItem.Update` и `TaskItem.ChangeStatus`: обязательность и длина полей, допустимые значения enum, нормализация email, обновление `updated_at`. Сущности имеют приватные сеттеры и не могут оказаться в невалидном состоянии.

## 5. Соответствие 12 факторам

### I. Кодовая база (Codebase)
Одна кодовая база в одном git-репозитории, из неё собираются все развёртывания: локальное через `make backend-run` / `make frontend-dev`, контейнерное через `make up` и тестовое. Backend и frontend — два процесса одного приложения, и версионируются они вместе, поэтому монорепозиторий здесь уместен. Разные окружения отличаются только конфигурацией, а не кодом.

### II. Зависимости (Dependencies)
Все зависимости объявлены явно и зафиксированы:
- NuGet: центральное управление версиями в `backend/Directory.Packages.props`, версия SDK зафиксирована в `backend/global.json`;
- инструмент миграций `dotnet-ef` закреплён локальным манифестом `.config/dotnet-tools.json` (`dotnet tool restore`), глобальная установка не требуется;
- npm: `package.json` вместе с `package-lock.json`, в Docker используется `npm ci`;
- системные зависимости изолированы в образах (`sdk:8.0-alpine` → `aspnet:8.0-alpine`, `node:22-alpine` → `nginx:alpine`).

Приложение не рассчитывает на системные утилиты хоста. Даже хеширование паролей реализовано средствами BCL, без внешних библиотек.

### III. Конфигурация (Config)
Всё, что различается между окружениями, передаётся через переменные окружения:
`ConnectionStrings__Default`, `Jwt__Secret`, `Jwt__Issuer`, `Jwt__Audience`, `Jwt__LifetimeMinutes`, `ASPNETCORE_HTTP_PORTS`, `Logging__Console__FormatterName`; для nginx — `PORT`, `API_UPSTREAM`, `DNS_RESOLVER`.
- Секретов в репозитории нет: `appsettings.json` содержит только безопасные значения по умолчанию, `.env` в `.gitignore`, в git хранится лишь `.env.example`.
- При старте конфигурация проверяется (`ValidateOnStart`): без строки подключения или с секретом JWT короче 32 байт процесс сразу завершится с понятной ошибкой.
- Frontend обращается к API по относительному пути `/api`, поэтому адрес API не вшивается в бандл при сборке. Один и тот же образ `web` работает в любом окружении, а upstream задаётся переменной `API_UPSTREAM` при запуске.

### IV. Сторонние службы (Backing services)
PostgreSQL — подключаемый ресурс. Приложение знает о нём только строку подключения из окружения. Чтобы заменить локальный контейнер на управляемую БД в облаке, достаточно поменять `ConnectionStrings__Default`, код менять не нужно. Готовность ресурса проверяется `/health/ready` через `AddDbContextCheck`.

### V. Сборка, релиз, выполнение (Build, release, run)
Стадии разделены:
- **Build:** multi-stage Dockerfile собирает неизменяемые образы `task-manager-api` и `task-manager-web` (`make build`);
- **Release:** образ получает тег короткого SHA коммита (`IMAGE_TAG`, по умолчанию `git rev-parse --short HEAD`) и объединяется с конфигурацией из `.env`. Каждый релиз однозначно идентифицируется, и откатиться можно, запустив предыдущий тег;
- **Run:** `docker compose up` запускает релиз. Изменить код на стадии выполнения невозможно: образы не содержат SDK и исходников.

### VI. Процессы (Processes)
API — stateless-процесс, который ничего не хранит в памяти или на локальном диске между запросами:
- аутентификация через самодостаточный JWT, поэтому любая реплика может обработать любой запрос без sticky sessions;
- выход из системы не держит «сессию» в памяти процесса: отозванные `jti` лежат в PostgreSQL, и их видят все реплики (проверено: после logout все три реплики отвечают `401`);
- всё состояние хранится только в сторонней службе, то есть в PostgreSQL.

### VII. Привязка портов (Port binding)
Сервисы самодостаточны и экспортируют HTTP через собственный порт:
- API поднимает встроенный веб-сервер Kestrel на порту из `ASPNETCORE_HTTP_PORTS` (8080 в контейнере, `API_PORT` локально). Внешний сервер приложений ему не нужен;
- web (nginx) слушает порт из переменной `PORT`, а на хост публикуется `APP_PORT`.

### VIII. Параллелизм (Concurrency)
Масштабирование идёт горизонтально, через процессы:
- `make scale-api N=3` запускает несколько реплик API. Сервис `api` не публикует фиксированный порт хоста, поэтому реплики не конфликтуют;
- nginx обращается к `api` через Docker DNS (`resolver 127.0.0.11 valid=10s` и переменная в `proxy_pass`), так что новые реплики подхватываются без перезапуска и получают трафик по round-robin;
- типы процессов разделены: web-процесс (`api`), разовый admin-процесс (`migrator`), статика и proxy (`web`).

Это задел под будущее задание по балансировке трафика.

### IX. Утилизируемость (Disposability)
- Быстрый старт: API запускается примерно за секунду (alpine-образ, без прогрева и тяжёлой инициализации). Миграции вынесены из старта в отдельный процесс, поэтому старт не ждёт схему БД;
- корректное завершение: по `SIGTERM` ASP.NET Core Generic Host перестаёт принимать соединения и дожидается текущих запросов (`HostOptions.ShutdownTimeout`), `CancellationToken` пробрасывается до запросов EF Core; nginx также корректно завершается по `SIGQUIT`/`SIGTERM`;
- процессы можно убить в любой момент без потери данных: всё состояние в PostgreSQL, запись атомарна в рамках `SaveChanges`. `restart: unless-stopped` и health-checks позволяют оркестратору перезапускать процессы.

### X. Паритет разработки и продакшена (Dev/prod parity)
- Везде используется одна и та же СУБД одной версии, PostgreSQL 16: в compose, при локальной разработке (`make db-up`) и в интеграционных тестах (Testcontainers поднимает `postgres:16-alpine`). SQLite или InMemory-провайдер вместо «боевой» БД не используется, и поведение `ILIKE`, `pg_trgm` и ограничений одинаково во всех средах;
- одни и те же образы используются локально и на сервере, окружения различаются только переменными;
- `make up` за одну команду поднимает окружение, идентичное продакшен-топологии.

### XI. Журналирование (Logs)
Приложение не управляет файлами логов, а пишет поток событий в `stdout`:
- в контейнерах включён структурированный JSON-формат (`Logging__Console__FormatterName=json`), локально — человекочитаемый `simple`;
- сбором, хранением и маршрутизацией занимается среда выполнения: `docker compose logs`, а в будущем Loki или ELK. Приложение ничего не знает о получателе логов;
- nginx также пишет access и error логи в stdout и stderr (поведение официального образа).

### XII. Задачи администрирования (Admin processes)
Административные задачи запускаются как разовые процессы из того же образа, с тем же кодом и той же конфигурацией, что и основной процесс:
- `dotnet TaskManager.Api.dll migrate` применяет миграции EF Core. В compose это сервис `migrator`: он завершается с кодом 0, и только после этого стартует `api` (`service_completed_successfully`). Вручную: `make migrate`;
- `dotnet TaskManager.Api.dll purge-revoked-tokens` удаляет истёкшие отозванные токены (`make purge-tokens`);
- при разработке миграции управляются через Makefile: `migration-add`, `migration-remove`, `migration-list`, `migration-script`, `db-update`, `db-rollback`.

Код миграций хранится в репозитории вместе с приложением (`Infrastructure/Persistence/Migrations`), поэтому схема БД версионируется вместе с кодом.

**Итог:** приложение соответствует всем 12 факторам, исключений нет.

## 6. Запуск

```bash
make env        # создать .env из .env.example (при необходимости поменять секреты)
make up         # собрать образы, применить миграции, поднять db + api + web
```

Приложение: http://localhost:8080 (порт задаётся `APP_PORT`).

Локальная разработка:

```bash
make db-up && make db-update   # PostgreSQL в контейнере и миграции
make backend-run               # API на http://localhost:5080
make frontend-dev              # Vite на http://localhost:5173 с proxy /api
```

Тесты: `make test`. Юнит-тесты домена и хеширования, интеграционные тесты API на реальном PostgreSQL через Testcontainers; нужен запущенный Docker. Сейчас 38 тестов.

## 7. Развёртывание в Kubernetes (minikube)

Приложение развёрнуто в локальном кластере minikube (драйвер `docker`, Kubernetes v1.34). Образы `task-manager-api:5e37ca7` и `task-manager-web:5e37ca7` собраны из тех же Dockerfile, что и для compose, и загружены в кластер командой `minikube image load`. Туда же заранее загружен `postgres:16-alpine`. Во всех манифестах указан `imagePullPolicy: IfNotPresent`, поэтому кластер берёт образы из своего локального хранилища и не обращается к внешнему реестру.

Манифесты лежат в `k8s/`:

| Файл | Объекты |
|---|---|
| `configmap.yml` | ConfigMap `task-manager-config` |
| `db.yml` | headless Service `db`, StatefulSet `db` |
| `migrate-job.yml` | Job `migrate` |
| `api.yml` | Service `api`, Deployment `api` |
| `web.yml` | Service `web`, Deployment `web` |

### 7.1. Использованные абстракции Kubernetes

| Абстракция | Объект | Для чего используется |
|---|---|---|
| **Secret** | `task-manager-secrets` | Хранит `POSTGRES_PASSWORD` и `JWT_SECRET`. Создаётся из `.env` командой `kubectl create secret generic task-manager-secrets --from-env-file=.env`, поэтому секреты не попадают в git. В контейнеры передаются через `env[].valueFrom.secretKeyRef` |
| **ConfigMap** | `task-manager-config` | Несекретная конфигурация: `POSTGRES_DB`, `POSTGRES_USER`, `JWT_ISSUER`, `JWT_AUDIENCE`, `JWT_LIFETIME_MINUTES`. Передаётся через `configMapKeyRef` |
| **StatefulSet** | `db` (1 реплика) | PostgreSQL. В отличие от Deployment, даёт поду стабильное имя `db-0` и закрепляет за ним собственный диск: после пересоздания под подключается к тому же тому |
| **PersistentVolumeClaim** | `data-db-0` (1Gi, `ReadWriteOnce`) | Создаётся из `volumeClaimTemplates` StatefulSet. Том выделяет `storage-provisioner` minikube (StorageClass `standard`). PVC не удаляется вместе с подом и StatefulSet, поэтому данные переживают перезапуск БД |
| **Job** | `migrate` | Разовый admin-процесс (фактор XII): запускает образ API с аргументом `migrate`, применяет миграции и завершается со статусом `Complete`. `restartPolicy: Never`, `backoffLimit: 6` — при ошибке (например, если БД ещё не готова) Job создаёт новый под; `activeDeadlineSeconds: 300` ограничивает общее время |
| **Deployment** | `api` (2 реплики), `web` (1 реплика) | Stateless-процессы. Deployment управляет **ReplicaSet**, а тот поддерживает нужное число **Pod**: упавший или удалённый под сразу пересоздаётся. Стратегия `RollingUpdate` с `maxSurge: 1`, `maxUnavailable: 0`: при обновлении образа новый под поднимается раньше, чем гасится старый, и сервис не простаивает |
| **Pod** | `db-0`, `migrate-*`, `api-*`, `web-*` | Минимальная единица запуска: контейнер, его сеть и тома. Напрямую поды не создаются, ими управляют контроллеры выше |
| **Service (ClusterIP)** | `api` (порт 8080) | Постоянный виртуальный IP и DNS-имя для набора подов `app=api`. Распределяет соединения между репликами |
| **Service (headless)** | `db` (`clusterIP: None`, порт 5432) | Обязателен для StatefulSet. DNS-имя `db` разрешается сразу в IP пода `db-0`, без виртуального IP |
| **Service (NodePort)** | `web` (80 → `nodePort: 30080`) | Точка входа снаружи кластера |
| **Probes** | у всех долгоживущих контейнеров | `readinessProbe` решает, можно ли слать трафик в под: пока проверка не прошла, под не попадает в Endpoints сервиса. `livenessProbe` перезапускает зависший контейнер. API: `/health/ready` (с проверкой БД) и `/health/live`; web: `/healthz`; db: `pg_isready` |
| **Resources** | requests и limits у каждого контейнера | `requests` используется планировщиком при размещении пода, `limits` ограничивают потребление CPU и памяти, чтобы один процесс не занял все ресурсы ноды |

Порядок развёртывания учитывает зависимости:

```bash
kubectl create secret generic task-manager-secrets --from-env-file=.env
kubectl apply -f k8s/configmap.yml -f k8s/db.yml
kubectl wait --for=condition=ready pod/db-0 --timeout=120s
kubectl apply -f k8s/migrate-job.yml
kubectl wait --for=condition=complete job/migrate --timeout=180s
kubectl apply -f k8s/api.yml -f k8s/web.yml
```

API не ждёт завершения Job сам, поэтому `kubectl wait` гарантирует, что к старту API схема БД уже создана.

### 7.2. Взаимодействие сервисов

```
                       kubectl port-forward svc/web 8080:80
 браузер ─────────────────────────────────────────────┐
 (localhost:8080)                                     ▼
                                          Service web (NodePort 30080)
                                                      │
                                                      ▼
                                           Pod web (nginx :80)
                                ├─ /, /assets/*  → статика React из образа
                                └─ /api/*        → proxy_pass
                                                      │  http://api.default.svc.cluster.local:8080
                                                      ▼
                                          Service api (ClusterIP :8080)
                                         kube-proxy выбирает под из Endpoints
                                         ┌────────────┴────────────┐
                                         ▼                         ▼
                                  Pod api-…(:8080)          Pod api-…(:8080)
                                         └────────────┬────────────┘
                                                      │  Host=db;Port=5432
                                                      ▼
                                       Service db (headless) → Pod db-0 (:5432)
                                                      │
                                                      ▼
                                              PVC data-db-0 (1Gi)

 Job migrate ── Host=db;Port=5432 ──▶ db-0   (один раз, перед запуском api)
```

1. **Вход снаружи.** Service `web` типа NodePort открывает порт 30080 на ноде minikube. При драйвере `docker` на Windows нода находится внутри контейнера и напрямую с хоста недоступна, поэтому используется туннель: `kubectl port-forward svc/web 8080:80` (приложение на http://localhost:8080) или `minikube service web --url`.
2. **web → api.** nginx отдаёт собранный фронтенд, а запросы `/api/*` проксирует на `API_UPSTREAM`. Внутри кластера используется полное имя `api.default.svc.cluster.local`: директива `resolver` в nginx не применяет search-домены из `/etc/resolv.conf`, и короткое имя `api` не разрешится. В качестве DNS-сервера указан kube-dns (`DNS_RESOLVER=10.96.0.10`, это адрес CoreDNS в minikube) вместо Docker DNS `127.0.0.11`, который используется в compose. Образ при этом не менялся: адреса задаются переменными окружения в манифесте (фактор III).
3. **Балансировка между репликами api.** Имя `api` разрешается в постоянный ClusterIP сервиса. kube-proxy настраивает на ноде правила, по которым каждое новое TCP-соединение на этот IP уходит на случайный под из Endpoints сервиса. В Endpoints попадают только поды, прошедшие `readinessProbe`, поэтому трафик не идёт в стартующую или потерявшую БД реплику. nginx не держит постоянных соединений с upstream (`keepalive` не настроен), поэтому каждый запрос открывает новое соединение и может попасть на любую реплику. Это допустимо, потому что API stateless (фактор VI): JWT проверяется любой репликой, а отозванные токены хранятся в БД.
4. **api → db.** Строка подключения `Host=db;Port=5432;…` собирается в манифесте из переменных ConfigMap и Secret через подстановку `$(VAR)`, поэтому пароль не записан открытым текстом. Headless Service `db` разрешается CoreDNS прямо в IP пода `db-0`. При пересоздании пода IP меняется, но имя остаётся тем же, а данные сохраняются на PVC.
5. **migrate → db.** Job подключается к БД по тому же имени и с той же конфигурацией, что и API, применяет миграции и завершается. Дальше в работе приложения он не участвует.

Все адреса внутри кластера — DNS-имена сервисов. IP подов нигде не прописаны, поэтому поды можно масштабировать (`kubectl scale deployment api --replicas=3`), удалять и пересоздавать без изменения конфигурации.
